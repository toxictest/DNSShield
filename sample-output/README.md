# DNSShield sample output

Everything here was produced by the tool itself.

| File | What it shows |
|---|---|
| `live-example.com/dns_security_audit.txt` | A live audit of `example.com` — hard-fail SPF, `p=reject` DMARC, DNSSEC enabled with a DS chain, no wildcard, AXFR refused on both name servers. |
| `live-github.com/dns_security_audit.txt` | A live audit of `github.com` plus three subdomains — 13 SPF mechanisms, `p=quarantine` DMARC, **6 working DKIM keys (5 of them reached through a CNAME to the mail provider)**, 8 name servers all refusing `AXFR`, and no DNSSEC. |
| `simulated-vulnerable/dns_security_audit.txt` | Every module firing at once: `+all` SPF, no DMARC, only a revoked DKIM key, two **dangling CNAMEs** (a deleted S3 bucket and a removed Heroku app), an **open `AXFR`**, no DNSSEC and a wildcard record. |
| `console-example.com.txt` | The terminal output, ANSI codes stripped. |
| `console-example.com.ansi.txt` | The same run with the colour codes intact. |
| `console-simulated-vulnerable.txt` | The vulnerable run, ANSI codes stripped. |
| `console-simulated-vulnerable.ansi.txt` | The vulnerable run with colour. |

## Why the vulnerable sample is simulated

A live dangling CNAME and a live open `AXFR` are both things that get fixed
the moment they are reported — there is no reliable example of either left on
the public Internet. The simulated report is generated by the same stub
resolver the test suite uses (`tests/make_sample_output.sh`), so it is
deterministic and exercises exactly the same code path as a real finding.

The two live reports are genuine resolver output.
